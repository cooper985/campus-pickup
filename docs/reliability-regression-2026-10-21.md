## 根因与证据

- 本轮使用用户提供的六张原始 JPEG，不是合成图。原图按字节保存到被 Git 忽略的 `test-data/private/ocr-regression-20261021/`，附原图及实际上传输入的 SHA-256。六图均超过512 KiB，经过现有微信原生压缩后为221138～344451字节，均通过原有服务端限制；没有改变图像质量策略或云函数。
- 第3图腾讯 OCR 成功返回“取件码”和“603402”，两行框分别为(174,1272,139,46)、(345,1272,223,52)。旧 `near()` 要求横向重叠，因此丢掉本应相邻横排的号码；前端误显示 arrived_no_code。修复后允许同排标签右侧号码，也保留纵向及跨栏距离限制。
- 第1图五个号码全部由 OCR 正确返回，旧坐标算法把站名只分配给最近的码，且允许后续站名抢占前一个码：186-139被误配到菜鸟驿站；不符合固定后缀的“亚开好时嘉”被漏掉。修复按同列地点区块承接连续取件码，只用明确地址/可靠站名及邻接地址支持陌生标题，后续明确地点有距离约束。品牌标题和分店名优先用具体分店，不拼接无关地点。
- 7fddd4f可提取第3图的码，但把地图城市和“物流求助”等当地点。6e0fa55和767b35d对真实六图的解析结果相同，均漏掉603402且误配186-139。说明解析退化在8dcd501的坐标规则中已经引入，不能全部归咎于767的并发，也不能整体回滚到旧的宽泛地点算法。
- 767把15秒整体等待降到10秒。用虚拟时钟复现11秒正常返回：稳定版接受，767丢弃，修复版接受。这是确定的提前丢弃机制；本轮开发者工具的两轮原图未发生真正超时，尚不能断言它解释了用户Android上的每一次失败。
