# 批量并发与已取记录删除验收（2026-10-21）

## 已实现

- 原页面 `runRecognition` 在 for 循环中逐张 await；慢图会推迟所有后续图片的启动。原单图前端等待 15 秒，`callFunction` 配置 20 秒。读取 base64 → 必要时压缩至 512 KiB 内 → 单次云调用 → 本地解析，不存在独立云存储上传。
- 新队列最多同时执行 3 个底层任务。每次尝试有独立 taskId、排队/读取/压缩/云端识别/结束状态、结果和错误；完成即更新页面。单图跳过、取消、整批取消、单图手动重试均可用，不自动重试，不添加识别前的额外云调用。
- 前端等待采用 **10 秒测试值**，从实际开始处理计时，排队时间单独记录。超时或取消后不接受旧结果；底层调用结束前仍占用并发槽，防止重试堆积突破 3 次。微信云调用无法由此真正中止，仍可能消耗次数；全部槽被旧请求占用时，后续图会显示排队并可取消。
- 已完成草稿可先确认导入，其他图继续识别。导入只消费打开确认时的草稿快照，弹窗期间及之后的新结果保留；失败保留上次成功草稿并明确提示，合法无码结果替换该图旧草稿。
- 待取只显示“修改 / 我已取件”。已取右滑露出红色“删除”，另有“删除…”备用入口，保留“恢复待取”。删除需要按钮及确认弹窗两步操作。
- 右滑阈值 56 CSS 像素，横移必须大于纵移 1.5 倍；12 像素后锁定方向，多指及 touchcancel 取消，纵滚不阻断。一条展开、点击外部或滚动收起，滑动后 350 毫秒抑制误点击，确认期间阻止重复删除。
- 删除和撤销均调用原有 save + 读回校验；确认写入成功才改变看板。最近一次删除有 5 秒撤销，恢复原 ID/顺序/已取状态；再删除会在确认框说明替换上次撤销机会。撤销仅在当前页面进程的时间窗口内有效，重启不保留撤销缓存。存储异常进入原有保护状态，不显示虚假成功。
- `pickup-store.js`、存储 version:1、去重服务和所有云函数保持原样。没有迁移、部署、权限或计费修改，没有远端推送。

## 六次真实 OCR 对照（毫秒）

开发者工具选择三张已有无个人信息的**合成 PNG**：运输中、到站有码、到站隐藏码。每张串行和并发各一次，均返回 ok:true、mock:false；只产生 1 条正确草稿，两张无码 count=0。未确认导入。

串行对照用相同适配器、解析器和当前页面 startImage 逐张 await，复现旧调度；并发通过当前 recognizeCloud 完整路径。对照均采用 10 秒前端上限。不是两组真机测量，也不是恢复旧云函数部署。

| 指标 | 图1 运输无码 串/并 | 图2 到站有码 串/并 | 图3 到站隐藏码 串/并 |
| --- | ---: | ---: | ---: |
| 结果实际渲染回调距批次开始 | 3737 / 885 | 4637 / 2736 | 5407 / 4536 |
| 单图开始到处理完成 | 3720 / 870 | 876 / 2702 | 768 / 4505 |

处理总计：5393 → 4526 ms。全部结果显示：5407 → 4536 ms，单轮约缩短 16.1%。实际客户端同时在途峰值：1 → 3。图2提早显示，但并发图2、3的单图云往返反而更长，不能承诺各图都更快。

可确认的瓶颈是原客户端串行排队，以及占主要时间的云往返。云往返包含传输、平台调度/可能的冷启动、函数与响应时间；尚无证据进一步区分。只有单轮、先串行后并发，受冷暖启动和网络波动影响，不可将 16.1% 当成稳定收益。6 次没有误超时，不足以证明 10 秒适合所有真机网络。
